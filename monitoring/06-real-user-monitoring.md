# Real User Monitoring (RUM)

## Introduction

Applications exist to serve users.

An application may appear healthy from an infrastructure perspective:

* CPU Usage = Normal
* Memory Usage = Normal
* Network = Healthy

However, users may still experience:

* Slow Page Loads
* Broken Features
* Login Failures
* Poor Mobile Experience
* Checkout Problems

Traditional monitoring focuses on systems and applications.

Real User Monitoring (RUM) focuses on the actual experience of users interacting with an application.

RUM provides visibility into:

* User Experience
* Performance
* Availability
* User Behavior
* Geographic Performance
* Device Performance

It answers one of the most important questions in observability:

```text
How are real users experiencing my application?
```

# What is Real User Monitoring?

## Definition

Real User Monitoring (RUM) is the process of collecting and analyzing performance data generated by actual users while they interact with an application.

Unlike synthetic monitoring, RUM measures real-world user experiences.

RUM captures:

* Actual User Activity
* Actual Devices
* Actual Browsers
* Actual Network Conditions
* Actual Locations

This provides a realistic view of application performance.

---

# Why RUM Matters

Consider an online shopping platform.

Infrastructure metrics show:

```text
CPU Usage = 45%
Memory Usage = 50%
Availability = 100%
```

Everything appears healthy.

However:

```text
Customers report:
Checkout is slow
```

RUM reveals:

```text
Checkout Page Load Time
= 8 Seconds
```

The issue becomes visible only when monitoring the user experience.

# How RUM Works

A small monitoring script or agent is embedded within an application.

Example:

```text
User Browser
      │
      ▼
Application Page
      │
      ▼
RUM Agent Captures Data
      │
      ▼
Monitoring Platform
```

The monitoring platform then analyzes user interactions.

# Core Web Vitals

Google introduced Core Web Vitals to measure user experience.

---

## Largest Contentful Paint (LCP)

Measures loading performance.

Goal:

```text
Less Than 2.5 Seconds
```

---

## First Input Delay (FID)

Measures responsiveness.

Goal:

```text
Less Than 100 ms
```

---

## Interaction to Next Paint (INP)

Modern replacement for FID.

Measures overall responsiveness.

Goal:

```text
Less Than 200 ms
```

---

## Cumulative Layout Shift (CLS)

Measures visual stability.

Goal:

```text
Less Than 0.1
```
